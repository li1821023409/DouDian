# 拉取项目后必读

> 换了电脑、重装了系统、或者重装了 OpenClaw 之后，按本文档从第 1 步走到第 5 步。
> 整个项目**不能只靠 `git clone` 就跑起来**——有一批东西在仓库外，必须单独恢复。

---

## 一、先认清：哪些东西不在仓库里

`git clone` 之后你会得到代码、脚本、文档，但**拿不到**下面这些。

| 缺失内容 | 在哪 | 为什么不在仓库 | 恢复方式 |
|---|---|---|---|
| **OpenClaw 的两个技能说明书** | `~/.openclaw/workspace/skills/` | OpenClaw 只读这个目录，与项目目录平行，git 管不到 | 跑 `scripts\install_skills.py`（**最容易被忘，忘了技能完全不生效**；只装 SKILL.md，代码仍在仓库 `scripts\`） |
| **OpenClaw 工作区约定 `AGENTS.md`** | `~/.openclaw/workspace/AGENTS.md` | 是 OpenClaw 的运行时目录，同级还有 `SOUL.md` / `USER.md` / `memory\` 等私人内容，不能放进项目仓库 | 把**附录 A** 整段追加到该文件末尾（漏了会让 agent 反复试探脚本位置，实测撑爆上下文） |
| **video-cleaner 运行环境** | `video-cleaner\.venv`（4.3G） | 数万个小文件，git 快照存储会让仓库爆炸 | 跑 `video-cleaner\setup_env.py` |
| **ffmpeg 便携版** | `video-cleaner\tools`（497M） | 二进制，单文件超 100MB | 同上脚本自动下载 |
| **LaMa ONNX 模型** | `video-cleaner\models\lama_fp32.onnx`（208M） | 超 GitHub 单文件 100MB 上限 | 同上脚本自动下载 |
| **LaMa GPU 权重** | `video-cleaner\models\big-lama.pt`（205M） | 同上，且公开源只有原始 `.ckpt` | **只能手工拷贝**（U 盘/网盘/旧机器） |
| **抖店登录态** | BrowserOS 浏览器的 profile | 是账号凭证，绝不能进仓库 | 浏览器里手动登录 `fxg.jinritemai.com` |
| **LM Studio 模型** | LM Studio 自己的模型目录 | 与项目无关 | 在 LM Studio 里下载 `qwen3.5-9b` |
| 商品导出表 | `商品数据\*.xlsx` | 每日生成的数据 | 跑导出技能自动生成 |
| 下载的短视频与商品主图 | `带货短视频\` | 体积大且可重新下载 | 跑流水线自动生成 |

**仓库里已经有的**（不用额外处理）：全部 Python 脚本、技能定义（`抖店管理工作流\skills\`）、
晓风插件源码（`插件\晓风运营插件-30.3.3\`）、5 个水印模板 PNG、全部文档。

## 二、五个步骤，按顺序做

### 第 1 步：装基础软件

| 软件 | 版本要求 | 说明 |
|---|---|---|
| Python | 3.13 | 装在 `D:\Install\Python\`（脚本里的路径写死了这个位置） |
| OpenClaw | 任意较新版本 | 首次启动会生成 `~/.openclaw/` |
| BrowserOS neo | — | 抖店操作全靠它，端口 9010 / 9110 |
| LM Studio | — | 加载 `qwen/qwen3.5-9b`，开本地服务（端口 1234） |

> ⚠️ **所有脚本都假设项目在 `D:\Data\DouDian`**。如果放在别处，
> 需要改 `scripts\*.py` 里的 `PROJ` / `ROOT` 常量（每个脚本顶部都有）。

**关于 BrowserOS neo 装在哪（结论：装在默认位置，不要挪进仓库）**

它装在 `C:\Users\<你>\AppData\Local\BrowserClaw\`（约 2.5G：程序 500M + profile 2G）。
曾经考虑把它挪到 `D:\Data\DouDian\` 下统一管理，**不建议**，原因：

| 理由 | 说明 |
|---|---|
| 不能进 git | 2.5G 二进制 + profile（含抖店登录 cookie），一旦误提交就再也删不干净 |
| 路径被三处绑定 | 快捷方式、profile 默认位置（`%LOCALAPPDATA%\BrowserClaw\User Data`）、卸载/更新记录；手工搬完必须加 `--user-data-dir` 启动参数，否则等于换了个空 profile，登录态全丢 |
| 会被更新打回原形 | 它是 Chromium 分叉，版本装在 `Application\<版本号>\`，升级会往默认位置写新版本，最终变成 C/D 两份 |
| 没必要 | C 盘余量充足，省这 2.5G 没有实际收益 |

真正值得统一的是**代码路径**：仓库 `scripts\` 唯一一份，技能和定时任务都指向它。
如果哪天真想换盘，正确做法是重装到目标盘、再用 `--user-data-dir` 指过去，而不是复制文件夹。

### 第 2 步：恢复 OpenClaw 技能

```bat
D:\Install\Python\python.exe D:\Data\DouDian\scripts\install_skills.py
```

**只有一份代码**：所有脚本都在仓库 `scripts\`，技能目录只放说明书（`SKILL.md`）。

```
D:\Data\DouDian\scripts\                          ← 唯一代码真源（.py 全在这）
D:\Data\DouDian\抖店管理工作流\skills\<技能名>\   ← 只有 SKILL.md（+ 说明文档）
   ↓ install_skills.py（把 {{PROJ}} 替换成实际仓库路径后复制）
C:\Users\<你>\.openclaw\workspace\skills\<技能名>\ ← OpenClaw 读这里，同样只有 SKILL.md
```

装完**重启 OpenClaw**（技能定义启动时加载）。技能里所有命令都是仓库 `scripts\` 的绝对路径，
所以**不要再把 .py 复制进技能目录**——那样必然出现两份代码、改一份不生效。

### 第 2.5 步：确认定时任务指向仓库脚本

```bat
openclaw cron list
```

| 任务 | 应当指向 |
|---|---|
| 抖店短视频榜单-每日 | `D:\Data\DouDian\scripts\compass_video_rank.py` |
| 抖店数据导出-每日 | `D:\Data\DouDian\scripts\doudian_export.py` |

这两个任务是**命令型任务**（直接执行 .py，不走模型），路径写死在任务里。
如果哪天把脚本挪了位置，必须同步改任务，否则每天都会报 `can't open file ... [Errno 2]`：

```bat
openclaw cron edit <任务ID> --command-argv "[\"D:/Install/Python/python.exe\",\"D:/Data/DouDian/scripts/xxx.py\"]" --command-cwd "D:/Data/DouDian/scripts"
```

### 第 2.6 步：把执行约定写回 AGENTS.md

`AGENTS.md` 位于 `C:\Users\<你>\.openclaw\workspace\AGENTS.md`，**不在本项目仓库**，
`git clone` 拿不到它，`install_skills.py` 也不会装它。

新机器上它是 OpenClaw 自动生成的默认模板，只有通用的记忆与红线规则，**缺少本项目的执行约定**。
打开文件，把**附录 A** 那段原样追加到末尾即可。OpenClaw 每次会话都重读，无需重启。

> ⚠️ 漏掉这一步**不会报错**，但 agent 会退回「自己找脚本」的模式：
> 先 `tool_search`（一次把上万字符的工具清单塞进上下文），再连续 `process poll` 40+ 次，
> 单轮就把历史顶到约 22k token，几轮后整体超限卡死。2026-10-26 实际发生过一次，
> 症状见第四章第 5 条。

### 第 3 步：恢复去水印环境

## 四、最容易踩的五个坑

**1. 忘了装技能，OpenClaw 说“没有下载脚本”**
OpenClaw 只看 `~/.openclaw/workspace/skills/`。跑 `install_skills.py` 并重启。

**2. 重启电脑后插件丢了，抓到 0 个商品**
未打包扩展不会自动恢复。症状：页面正常显示商品列表，但 `probe_page.py` 的 `itemPers` 为 0。

**流水线已自动处理**，顺序是这样（顺序本身很关键，别随意调整）：

```
⓪.5  ensure_extension --load    只把扩展加载好，不碰页面
①    打开榜单页                  新页面会自动注入，无需刷新
①.5  ensure_extension --check   只验证，不修复
②    抓取
```

**为什么是这个顺序**：如果先打开页面再修插件，修完必须刷新才能注入；
而**刷新会把榜单 tab 从「短视频榜」重置回「总榜」**——这时抓取拿到的是商品榜数据，
`videourls` 属性为空，表现为「200 个商品 / 0 个视频」，最后下载 0 个文件。
这是 2026-10-25 实际踩过的坑，改顺序后才正常。

**一眼判断抓的是哪个榜**：看表头。
出现「排名 / 商品 / 店铺名称 / 用户支付金额 / 点击次数 / 成交件数」= 商品榜，抓不到视频。

单独排查时按需选择：

```bat
:: 只确保扩展加载（不碰页面、不刷新，可随时安全执行）
D:\Install\Python\python.exe D:\Data\DouDian\scripts\ensure_extension.py --load

:: 只检查页面是否注入（不刷新）
D:\Install\Python\python.exe D:\Data\DouDian\scripts\ensure_extension.py --check

:: 检测 + 修复（会刷新！刷新后 tab 重置，需重跑 compass_video_rank.py）
D:\Install\Python\python.exe D:\Data\DouDian\scripts\ensure_extension.py
```

三种情况的判定与退出码（0 表示正常）：

| 情况 | 判断依据 | 动作 | 退出码 |
|---|---|---|---|
| 插件源缺失（真没装） | `插件\晓风运营插件-30.3.3\manifest.json` 不存在 | 提示 `git checkout -- 插件/` | 2 |
| 源在但被拦截 | 页面 `itemPers` 为 0 | `--load` 只加载；默认模式加载+刷新+复检 | 5 / 6 |
| 已生效 | `itemPers` > 0 | 直接通过 | 0 |

服务没起来时（BrowserOS / MCP 未运行）退出码 3，并明确提示先启动浏览器。

**额外排查工具**：`probe_attrs.py` 可以打印插件在 `<p itemid>` 上注入了哪些属性，
其中 `videourls` 是否为空，直接决定能不能抓到视频。

**3. 命令行 curl 本地地址返回 502**
是环境代理拦截，不是服务坏了。加 `NO_PROXY=localhost,127.0.0.1`，或 `curl --noproxy "*"`。

**4. 隔夜复用旧链接，全部 403**
抖音 CDN 直链带签名，几小时就过期。必须重跑 `fetch_rank.py` 重新抓，
不能直接拿旧的 `商品数据\短视频榜单_抓取.json` 下载。

**5. 工作流一直转圈，其实是会话上下文超限（不是脚本卡住）**

症状：在 OpenClaw 里说完话，界面永远转圈；`带货短视频\` 没有新文件，
说明请求**根本没进到执行阶段**，脚本一条都没启动。

判断依据是会话库里的错误事件（`transcript_events` 的 `errorCode`）：

```
stopReason: "error"
errorCode: "context_length_exceeded"
estimated input 32953 leaves only 0 output tokens within the 32768-token context
```

根因几乎都不是"模型太小"，而是**单轮灌进了太多工具结果**——`AGENTS.md` 里路径写错 →
agent 找不到脚本 → `tool_search` 拉全量工具清单 → 反复 `process poll`。
治本是把 `AGENTS.md` 按**附录 A** 修好；治标用纯截断压缩（不调用模型，
绕开"压缩本身也超限"的死循环）：

```bat
openclaw sessions compact "agent:main:main" --max-lines 60 --timeout 120000
```

> 单纯调大 `contextWindow` 治不了这个问题：历史仍在无限累积，只是推迟爆掉的时间。

## 五、判断“任务真的完成了”的方法

本地模型（Qwen3.5-9B）会过度自信，脚本失败也常说“已完成”。**只看文件，不看它的话**：

| 检查项 | 说明 |
|---|---|
| `带货短视频\_下载清单.json` | 存在且时间戳是刚才 → 下载真跑了 |
| `商品数据\短视频榜单_抓取.json` 的 `fetched_at` | 是今天 → 抓取真跑了 |
| `带货短视频\商品名\` 里的 mp4 数量和体积 | 每条几 MB 到几十 MB，若只有几百 KB 或 4.5 秒，说明编码失败 |
| `带货短视频\商品名\` 里有没有 `_主图.jpg/png` | 有 → 商品主图下载成功（来源是抓取数据的 `pic` 字段） |
| 成品文件名带 `_去水印版` | 后缀对 → 走的是去水印流程 |

### 推送失败的排查（本次实际遇到）

**症状**：

```
fatal: unable to access 'https://github.com/li1821023409/DouDian.git/':
schannel: failed to receive handshake, SSL/TLS connection failed
```

**原因**：GitHub 直连被阻断，TCP 能连上但 TLS 握手被切断。Git 没有走代理就会这样。
`schannel` 是 Windows 自带的 TLS 实现，git for Windows 默认用它，这个报错不代表证书有问题。

**先确认代理可用**：

```bat
:: 看代理端口是否在监听（Clash 默认 7897）
netstat -ano | findstr ":7897"

:: 看代理能否连通 GitHub，返回 200 Connection established 即正常
curl -I -x http://127.0.0.1:7897 https://github.com
```

**再确认 git 用了代理**：

```bat
git config --global --get http.proxy
:: 应输出 http://127.0.0.1:7897
```

**临时强制走代理推送**（不改配置）：

```bat
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin master
```

**如果换成代理仍然报 schannel 握手失败**（2026-10-25 实际遇到，curl 经同一代理能返回 200，
但 git 就是握手失败），是 Windows 自带的 schannel TLS 后端与代理隧道不兼容，改用 OpenSSL：

```bat
git -c http.sslBackend=openssl -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin master
```

嫌长可以永久配置一次（OpenSSL 是标准实现，一般无副作用）：

```bat
git config --global http.sslBackend openssl
```

**GUI 工具（GitHub Desktop / TortoiseGit / VS Code）报同样的错怎么办**

2026-10-26 实测：GitHub Desktop 3.5.3 内置 git 2.47.3 **读的就是同一份 `~/.gitconfig`**
（`http.proxy` 和 `http.sslBackend` 都能读到）。它报 schannel 握手失败，原因不是"不读全局代理"，
而是当时的全局 `http.sslBackend` 仍是 `schannel`。把全局后端改成 openssl 后，命令行推送成功，
Desktop 也随之恢复——**不用重启，也不用在 Desktop 里另外填代理**。

怀疑 GUI 读错了配置时，直接问它自己的 git（版本号按实际目录替换）：

```bat
"C:\Users\<你>\AppData\Local\GitHubDesktop\app-3.5.3\resources\app\git\cmd\git.exe" --version
"C:\Users\<你>\AppData\Local\GitHubDesktop\app-3.5.3\resources\app\git\cmd\git.exe" config --global --get http.sslBackend
:: 输出 openssl 即已生效；输出 schannel 或空，就是问题所在
```

只有两者**输出不一致**时，才说明它用了自己的配置或内置 git，这时再去该 GUI 的网络设置里单独填。

排除顺序建议：**代理端口 → 全局 `http.proxy` → 全局 `http.sslBackend` → 最后才怀疑 GUI 自身**。
