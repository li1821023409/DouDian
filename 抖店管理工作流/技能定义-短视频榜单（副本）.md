## 维护信息（仅在用户要求修改代码时才需要读）

脚本：`D:\Data\DouDian/scripts/compass_video_rank.py`，纯标准库，复用
`doudian_export.py` 的 McpSession（登录态、断线重连、页面清理）。

已处理的坑（改代码前必读）：

- **SSE 多帧解析**：browseros 的 streamable-http 返回多个 `data:` 帧，
  `RobustSession._post` 按 id 扫描全部帧取对应 JSON，否则 `tabs` 等调用
  会返回 None。
- **evaluate 参数**：`code` 参数按语句执行不返回表达式值，取返回值用
  `func` 参数（箭头函数）。
- **untrusted 包裹**：evaluate 结果被 `[UNTRUSTED_PAGE_CONTENT]` 包裹，
  `js_eval` 剥掉标记行再取 JSON。
- **选中态判定**：榜单 tab 的 active 类在祖先层（`aurora-tabs-tab-active`），
  品牌 tag 的 active 在叶子节点自身（`activeItem-eBkSoc`），两者判定方式不同，
  不能混用。
- **DOM 合成事件**：对抖店/罗盘的 React 菜单路由无效，但品牌 tag 的
  `el.click()` 有效。菜单跳转要依赖 URL 直达或 snapshot 拿 ref 用 act。

## 📐 千川素材规格（下载完自动统一，不需要额外要求）

下载到的抖音直链**经常不符合巨量千川的上传要求**，所以 `run_pipeline.py` 在下载后
会自动跑 `qianchuan.py` 把视频统一成合规规格。这一步**不需要用户开口**，
因为它是提交素材的硬性前提；只有用户明确说"不用转"才加 `--no-qianchuan`。

| 类型 | 宽高比 | 分辨率 | 码率 | 时长 | 体积 |
|---|---|---|---|---|---|
| 竖版 | 9:16 | 720x1280 ~ 1440x2560 | ≥ 516kbps | 4~300s | ≤ 1000M |
| 横版 | 16:9 | 1280x720 ~ 2560x1440 | ≥ 516kbps | 4~300s | ≤ 1000M |

**处理方式：原地替换，文件名不变。**
不产生 `_千川.mp4` 之类的新文件，目录里每条视频始终只有一份。

| 情况 | 处理 |
|---|---|
| 本来就合规（如 720x1280） | **跳过不转**，重编码只损失画质 |
| 分辨率不足（如 540x960、576x1024） | 等比放大到 720x1280 |
| 高度差几个像素（如 720x1270） | 补黑边到 720x1280，不裁画面 |
| 码率 < 516kbps 或体积 > 1000M | 调码率重编码 |
| 时长 < 4s 或 > 300s | **无法修复**，只报告，不动文件 |

实测数据（2026-10-26，72 条视频）：宽高比、时长、码率、体积全部合规，
**只有分辨率不达标**——576x1024 占 32 条、540x960 占 8 条、720x1270/1278 各 4 条，
其余 24 条 720x1280 本就合规。处理后 72 条全部通过规格检查。

> 转码前后**文件名完全一样**，所以按名字对不上"哪条是被转过的"。
> 需要追溯时看 `带货短视频\_千川清单.json`（每次运行都会写）。
> 原片会被覆盖，若想留底请在跑之前自行备份。

### 为什么必须用专门的脚本，不能"点按钮 + upload"

千川的上传组件在点「点击上传」那一刻才 `document.createElement("input")`，
而且这个 input **从不插入 DOM**，直接调原生 `.click()` 弹系统文件对话框。
CDP 的 `DOM.setFileInputFiles` 只能作用于已挂载节点，所以常规的
「snapshot 找 ref → upload(ref)」根本喂不进文件——节点压根不在文档树里。

脚本的做法：改写 `HTMLInputElement.prototype.click`，发现游离的 file input 就把它
挂进上传抽屉（2×2 透明方块），并吞掉原生 click。这样不弹系统对话框，
CDP 能正常设置文件，页面自己的 onChange 逻辑照常触发。

### 几个实测结论

| 现象 | 说明 |
|---|---|
| 单次最多 100 个 | 抽屉上写「已选择 N/100」；72 个可以一次传完，但分批更好排错 |
| 上传耗时 | 3 个 / 74MB 约 1.5 分钟；72 个 / 1.6GB 约 30-40 分钟 |
| 上传完成后要勾选 | 传完的文件会自动勾上，但偶有漏勾；脚本提交前会核对勾选数并补勾 |
| 提交后必须回读核对 | 出现过「3 个都点确定成功、库里只进 1 个」，所以以库里真实出现为准 |
| 审核是异步的 | 刚传完审核状态是 `-`，过一段时间才有「审核通过 / 审核不通过」 |
| 列表每页 20 条 | 去重基准和审核状态都要**逐页读全**；只读第一页会把第 2 页起的老素材当成新的重传 |

### 几条硬事实

| 现象 | 说明 |
|---|---|
| 标签名**最多 10 个字** | 超了「确定」直接禁用，弹窗提示「标签名称不能超过10个字」。商品全名一般 20-40 字，所以脚本取**前 10 个字**（`--max-len` 可调，但别超过 10） |
| 截断会撞名 | 两个商品前 10 字相同就会被打成同一个标签，脚本开头会告警，需要区分就手动改 |
| 多选要**逐行点** | 一个 JS 里连点多个 checkbox 会失败（React 重渲染后旧节点失效，实测连点 3 行只中 1 行）。脚本改成一行一次点击，勾满后一次批量提交；10 条约 70 秒 |
| 提交后要刷新 | 表格不会自动刷新，脚本重新加载页面再回读 |
| 核对只看「标签」列 | 标签名是文件名前缀，拿整行文本判断必然命中，是假阳性；必须按表头定位到「标签」那一格 |
| 幂等 | 标签已存在不重复建；已打过的再加一次无副作用 |

每次运行写 `带货短视频\_千川标签清单.json`。

## 输出目录结构

```
D:\Data\DouDian\带货短视频\
├── <商品名>\                        一个商品一个文件夹（文件夹名 = 商品名）
│   ├── <商品名>_01.mp4              文件名 = 文件夹名_序号（不是 01.mp4）
│   │                                ← 下载后已在原地统一为千川规格，文件名不变
│   ├── <商品名>_02.mp4
│   ├── <商品名>_主图.png            商品主图（榜单里那一列缩略图的原图，jpg/png 看实际格式）
│   └── <商品名>_01_去水印版.mp4     去水印成品（默认保留原片，--replace 才替换）
├── _下载清单.json                   本次下载的商品、文件、主图清单
├── _千川清单.json                   千川规格统一记录（原分辨率 → 新分辨率）
├── _千川上传清单.json               上一次上传的结果（提交数、失败文件、耗时）
└── _去水印进度.json                 done / failed，断点续跑靠它
```

> · 文件名带商品名前缀，是因为每个商品都有自己的 01~10，`01.mp4` 一旦离开文件夹
>   就分不清是哪个商品的第几条。
> · **千川规格统一是原地替换**，不会出现 `_千川.mp4` 这种新名字；想知道某条
>   有没有被转过、之前是多少分辨率，查 `_千川清单.json`。
> · 商品主图从榜单数据里的 `pic` 字段直接下载，不用点进详情页；已存在会跳过。
> · `*.part.mp4` 是编码被中断留下的中间产物（没有 moov、放不了），可以直接删；
>   `batch_run.py` 每次启动会自动清掉它和历史上坏掉的成品。

## 前置条件与耗时

1. 浏览器必须已登录抖店（`fxg.jinritemai.com`），browseros-neo 需在 `127.0.0.1:9010` 监听。
2. 下载 10 个商品约 40 秒（99 条视频、约 1.3GB）。
3. 去水印：单进程约 42ms/帧，30 秒视频约 1 分钟；97 条约 3.1 小时，双进程约 1.6 小时。
4. 千川规格统一：10~45 秒/条（要看放大多少），4 并发下 48 条约 5 分钟；
   已经合规的视频跳过不转，所以重跑很快。
5. 抖音 CDN 直链带签名会过期，隔天必须重跑 ① ② 拿新链接，否则 403。

## 去水印的边界（如实告知用户）

- 只认「抖音号：」和「@账号名」两种水印形态；模板匹配有效帧低于 30% 时脚本会**跳过并保留原片**，
  不会输出带水印的成品，失败项记在 `带货短视频\_去水印进度.json` 的 `failed` 里。
- 分辨率特殊或水印排版差异大的视频（如 576×1024）可能识别不到，需要单独处理。
